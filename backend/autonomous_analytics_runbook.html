Autonomous Analytics Runbook

A business user types a question; the backend plans it, finds the matching KPI, writes and checks a SQL query, runs it on the right database and returns a written answer with a chart. This page shows the functions behind that and what a deployer has to provide.

Containers
Two: frontend (nginx, static React build) and backend (Node 22, Express).
You must provide
App MySQL, an LLM server with embeddings, a Microsoft Entra app registration.
State
App MySQL (5 tables) and one volume holding the vector index. The containers hold nothing else.
Answer time
1 to 5 minutes per question on a local LLM. Every step is a model call.

What talks to what

The browser calls two things directly. Only the backend reaches the databases, the LLM server and the vector index.

Startup

What the backend does between node dist/index.js and accepting traffic, and where it can stop.

One question, end to end

The same pipeline serves POST /api/chat and POST /api/chat/stream. The stream sends a progress event after each step and a final result event.

Model lifecycle

The semantic model (entities, KPIs, metrics, descriptions) is data in the app database, not code. Changing it is an operational action.

Gaps in the deploy files

Found by reading the Dockerfiles, compose file and code. I did not build the images or run compose.

  • Backend sign-in variables are not passed. docker-compose.yml gives the frontend build the VITE_AZURE_ENTRA_* values but gives the backend no AZURE_ENTRA_TENANT_ID or AZURE_ENTRA_CLIENT_ID, so a compose deployment answers 401 to every API call. They are also missing from the root .env.example.
  • nginx does not proxy the API. It serves static files only. The browser calls the backend directly at VITE_API_BASE_URL, so the backend needs its own public URL and FRONTEND_URL must match the frontend's.
  • Frontend settings are baked in. Changing the API URL or Entra ids needs an image rebuild, not a restart.
  • No health checks. Neither Dockerfile nor compose defines one, although /api/health exists. Add one on the backend; it only proves the process is up.
  • No schema migrations. initDb() creates missing tables only. A column change must be applied by hand.
  • One backend replica. The vector index is a JSON file with brute-force search, written by the process that rebuilds it. Do not run several replicas against separate copies.
  • Image excludes the index and .env. data and .env are in .dockerignore, which is right for secrets, but a new container always rebuilds the index and needs the embeddings endpoint at start.
  • Fine as is. Multi-stage builds, production dependencies only in the backend image, graceful shutdown on SIGTERM, JSON logs on stdout, and the app database needs no setup beyond credentials.
